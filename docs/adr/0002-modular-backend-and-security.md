# ADR-0002：模块化后端、JDBC 投影与 JWT 安全边界

## 状态

Accepted

## 背景

数据库已经覆盖 25 张消费者商城业务表，Vue3 前端已有完整页面，但 Java 侧只有用户 CRUD 和分类查询。项目运行在资源有限的单机服务器，未来还要为 Python AI 客服、运营 Agent 和数据中台提供受控接口。

## 决策

1. 保持单进程模块化单体，不拆分微服务。
2. 按业务能力组织代码并以应用服务作为事务边界。
3. 商品组合读取使用参数化 JDBC DTO 投影；用户聚合继续使用 JPA；强事务流程使用显式 SQL 条件更新。
4. 使用 Spring Security Resource Server 校验短时效 HS256 JWT，密码使用 BCrypt。
5. 真实支付以端口接口隔离；当前只提供可由配置关闭的本地沙箱实现。

## 结果

### 正面

- 单次部署和单库事务适合当前规模。
- 显式库存条件更新易于审计并防止超卖。
- DTO 投影避免为商品详情建立庞大双向 JPA 图。
- HTTP 安全边界可同时服务 Vue、AI 客服和未来运营工具。

### 负面

- JDBC 映射代码比自动 JPA 关联更多。
- HS256 密钥需要可靠的环境变量和轮换流程。
- 单体仍需整体部署，无法按模块独立扩缩容。

### 中性

- 未来需要外部身份提供方时，可替换令牌签发而保留 Resource Server 校验边界。
- 数据中台需要稳定后再通过 Outbox 或 CDC 接入。

## 已考虑的替代方案

- **全部 JPA 关联**：开发直观，但商品规格、图片、库存和订单历史容易产生 N+1 与序列化边界问题。
- **全部 JdbcTemplate**：控制精确，但会丢失现有用户 JPA 投资和部分领域映射价值。
- **立即微服务化**：当前服务器、团队和业务量不足以抵消分布式事务及运维成本。
- **内存会话令牌**：实现简单，但重启失效且不适合多实例。
