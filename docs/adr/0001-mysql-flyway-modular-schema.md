# ADR-0001：MySQL、Flyway 与模块化关系模型

## 状态

Accepted

## 背景

SUPER MALL 已有 Vue3 消费者前端，订单、库存、支付和售后需要强一致事务；当前团队规模小，服务器资源有限，同时计划未来接入 Python AI 客服、运营 Agent 和数据中台。现有项目使用 Spring Boot、JPA 与 MySQL，但由 Hibernate `ddl-auto=update` 自动改表，无法可靠审计或回滚数据库版本。

## 决策

1. 第一版采用 Spring Boot 模块化单体和单个 MySQL 事务数据库。
2. 使用规范化关系表表达商品、SKU、订单和履约关系，商品与地址在订单中保存快照。
3. 使用 Flyway 管理全部 DDL 与种子数据，JPA 改为 `ddl-auto=validate`。
4. 不在 MVP 中实现多商户和消息中间件，但保持模块边界并记录可审计状态历史。

## 结果

### 正面

- MySQL ACID 事务适合库存、订单和支付一致性。
- Flyway 让本地、测试和服务器数据库结构可重复、可追踪。
- 模块化单体易于学习、调试和部署，适合当前 2GB 服务器。
- 规范化 SKU 规格和独立状态历史支持前端查询与未来数据分析。

### 负面

- 单数据库暂时不能按模块独立扩缩容。
- 规范化规格表比 JSON 字段需要更多连接查询。
- 数据库迁移一旦应用不得原地修改，需要追加新版本修正。

### 中性

- 商品列表会保留评分、销量等聚合字段，明细表后续按功能增加。
- 多商户扩展需要新的商户与拆单迁移，但不会阻塞当前自营业务。

## 已考虑的替代方案

- **继续使用 `ddl-auto=update`**：开发快，但变更不可审计，生产风险高。
- **MongoDB 保存商品和订单文档**：规格灵活，但跨订单、库存和支付的事务及关系查询更复杂。
- **立即拆成微服务**：可独立扩容，但部署、事务和排错成本不适合当前规模。
- **SKU 规格完全存 JSON**：实现简单，但筛选、约束与数据中台分析能力较弱。
