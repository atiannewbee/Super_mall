# Super Mall 预发布全链路验收设计

## 目标

用真实浏览器验证预发布环境中消费者端、商家端、后端与 MySQL 的协作，
把核心交易链路固化为可重复执行的自动化测试，并将首轮发现的问题修复后
加入回归范围。

## 方案选择

### 方案 A：Playwright 黑盒测试（采用）

建立独立的 `apps/e2e` 工程，通过公网预发布域名操作两个 Vue 应用。测试不
导入前端内部实现，而是像真实用户一样注册、搜索、加购、下单、模拟支付，
再切换到商家端完成拣货和发货。该方案能同时发现路由、样式交互、接口、
鉴权、数据库状态机和部署代理问题，失败时保留截图、视频与 trace。

### 方案 B：继续扩充 Vitest 组件测试

执行快、无需测试账号，但只能证明组件在模拟数据下工作，无法验证 Nginx、
Cloudflare、后端和数据库，因此不能作为预发布验收依据。

### 方案 C：仅增加后端 API 集成测试

适合验证业务状态机，但无法覆盖页面元素、地址级联、购物车交互和跨端导航。
后端已经具备较完整的集成测试，本阶段继续只测 API 的收益较低。

## 架构

`apps/e2e` 使用 Playwright Test，默认指向：

- 消费者端：`https://mall-staging.350233.xyz`
- 商家端：`https://merchant-staging.350233.xyz`

地址、域名和商家凭据全部由环境变量覆盖。商家密码不得写入仓库、测试报告
或终端日志。测试数据使用 `E2E-<时间戳>` 前缀，方便在预发布数据库中识别。
完整交易测试串行执行，避免共享库存和订单状态相互干扰；公开页面冒烟测试
可以并行执行。

## 验收链路

1. 公开页面与健康接口可访问，浏览器控制台没有未处理错误。
2. 新消费者注册并保持登录状态。
3. 搜索商品、进入详情、加入购物车。
4. 新增收货地址并验证省、市、区级联结果。
5. 创建订单并完成模拟支付宝支付。
6. 商家登录，按订单号检索，开始拣货并填写物流发货。
7. 消费者刷新订单，看到物流信息并确认收货。
8. 消费者创建售后申请并在售后列表看到记录。
9. 商家新增、修改、搜索并软删除一件测试商品。

## 错误处理与证据

测试遇到失败时自动保留页面截图、视频和 Playwright trace，报告中不得包含
密码、JWT 或数据库密钥。网络请求失败必须展示接口路径、HTTP 状态和脱敏后
的响应摘要。包含商家登录的测试关闭 trace，避免网络请求体中的密码进入
artifact；这两条流程只保留失败截图和录像。公开页面测试仍可保留 trace。
每轮测试输出 HTML 报告，并在 GitHub Actions 手动验收任务中作为 artifact
保存。

预发布全链路测试使用手动触发，而不是每次 Pull Request 自动运行，避免未经
确认地持续创建真实预发布订单。常规 Pull Request 继续运行现有后端和两个
前端的隔离测试。
